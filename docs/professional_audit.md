# تدقيق احترافي أولي لمشروع CarRental

## النطاق

المشروع يتكون من API بـ ASP.NET Core، لوحة إدارة MVC، وتطبيق Flutter للعميل. الفرع الجاري هو `fix/portable-windows-config`.

## الحالة المؤكدة

- شجرة Git نظيفة عند بدء التدقيق.
- الحل يحتوي API وMVC وطبقات Domain/Application/Infrastructure وتطبيق Flutter.
- توجد اختبارات HTTP قديمة واسعة نسبيًا في `tests/test_api.sh`، لكنها لا تغطي مسارات حساب العميل الجديدة.
- توجد اختبارات Flutter محدودة لنماذج السيارة والإيجار والثيم فقط.

## الفجوات والمخاطر الأولية

| الأولوية | الملاحظة | الأثر |
|---|---|---|
| حرجة | `appsettings.json` يحتوي مفتاح JWT وكلمة مرور مدير افتراضيين معروفين | خطر أمني إذا استُخدمت الإعدادات خارج التطوير |
| عالية | `Cors:AllowedOrigins` فارغة، والـAPI يسمح بأي Origin عند الفراغ | غير مناسب للإنتاج ويحتاج فصل إعدادات التطوير عن الإنتاج |
| عالية | توثيق README ما زال يصف SQL Server وتدفقات حجز مجهولة قديمة | يضلل المستخدم ويخفي عقد العميل الجديد |
| عالية | اختبارات `tests/test_api.sh` لا تغطي `/api/customer-auth/*` ولا `/api/customer/rentals` ولا حدود الأدوار الجديدة | احتمال كسر رحلة العميل دون اكتشاف آلي |
| متوسطة | ترقية SQLite الحالية تعالج عمود `PasswordHash` فقط عبر SQL يدوي | صيانة المخطط ستصبح هشة عند إضافة تغييرات جديدة |
| متوسطة | اختبار Flutter الحالي محدود ولا يغطي تسجيل العميل أو Repositories أو الحجز أو التعامل مع 401/403 | تغطية غير كافية لتطبيق العميل |
| متوسطة | التشغيل المحمول يعتمد على المسارات النسبية وملف SQLite مشترك | يحتاج توثيقًا واختبارًا من مجلدات مختلفة حتى لا ينكسر التشغيل |
| عالية | وُجدت نسختان إضافيتان فارغتان من `car-rental.db` داخل `CarRental.API/` و`CarRental.Web/`، بينما تحتوي قاعدة الجذر على بيانات مختلفة | مؤشر على أن المسار النسبي قد ينشئ قاعدة خاطئة بحسب مجلد التشغيل، وقد تظهر لوحة MVC وAPI ببيانات مختلفة على جهاز جديد |
| منخفضة | رسائل بعض ProblemDetails والـSwagger ما زالت تذكر التدفق الإداري القديم | ارتباك للمطور والمستخدم |
| عالية | لا توجد حماية معدل طلبات لمسارات تسجيل دخول المدير أو العميل أو التسجيل | قابلية أعلى لهجمات التخمين وإغراق نقاط المصادقة |
| عالية | كلمة مرور المدير تُقارن مباشرة بإعدادات نصية ولا يوجد تخزين حسابات إدارة مجزأة | مناسب للتطوير فقط، لكنه ليس تصميمًا إنتاجيًا آمنًا |
| متوسطة | سياسة كلمة مرور العميل تفرض طولًا أدنى فقط ولا تفرض تعقيدًا أو تمنع المسافات/القيم الضعيفة | حسابات قابلة لإنشاء كلمات مرور ضعيفة |
| متوسطة | فحص تعارض الحجز ثم الإدراج وتغيير حالة السيارة منفصلان منطقيًا على مستوى الطلب، ولا توجد حماية واضحة من سباق طلبين متزامنين | قد يحدث حجز مزدوج في ضغط متزامن رغم صحة التدفق العادي |
| متوسطة | `DateTime.ToUniversalTime()` يتعامل مع تواريخ بلا منطقة زمنية وفق منطقة الخادم المحلية | اختلاف محتمل بين تاريخ الحجز الذي يراه العميل وما يُخزن فعليًا |
| متوسطة | لوحة MVC تستخدم `UseHttpsRedirection()` دون شرط وجود endpoint HTTPS، بينما التشغيل المحمول يعتمد HTTP | قد ينتج إعادة توجيه أو فشل تشغيل على جهاز جديد بلا شهادة تطوير |
| عالية | تطبيق Flutter لا يسجل الخروج تلقائيًا عند 401/403 ولا يحدّث كتالوج السيارات بعد إنشاء/إلغاء الحجز | جلسة منتهية وتجربة بيانات قديمة للمستخدم |
| متوسطة | تغطية Flutter الحالية لا تختبر المصادقة أو المستودعات أو الشاشات أو رسائل الأخطاء | أعطال واجهة العميل قد تمر دون اكتشاف |
| متوسطة | لا يوجد Seed رسمي قابل للتشغيل لإنشاء بيانات تجريبية مفهومة على نسخة جديدة | تجربة أول تشغيل تعتمد على إدخال يدوي وقد تبدو قاعدة البيانات فارغة |

## معيار الإصدار الاحترافي

لا يُعلن الإصدار جاهزًا قبل نجاح: بناء API وMVC، تحليل Flutter بلا أخطاء، اختبار تسجيل العميل ودخوله واستعادة الجلسة، إضافة سيارة من MVC وظهورها في Flutter، إنشاء وإلغاء حجز العميل، اختبارات منع الوصول المتبادل بين Admin وCustomer، وفحص الإعدادات الحساسة والتوثيق.

## ملاحظة منهجية

سيتم إصلاح المخاطر المؤثرة أولًا، ثم تحديث اختبارات HTTP وFlutter، ثم تحديث README وملفات التشغيل، وبعد ذلك يُعاد بناء الحل وتشغيل اختبارات القبول من طرف إلى طرف قبل تسجيل الإصدار.

## حالة الإصلاح بعد التدقيق

تم إغلاق المخاطر ذات الأولوية العالية والمؤثرة على التشغيل المحلي ورحلة العميل. نُقلت قيم JWT وكلمة مرور المدير إلى إعدادات التطوير فقط، وأضيف رفض صريح للإعدادات الافتراضية في بيئة الإنتاج، مع تقييد CORS في الإنتاج ومحدد معدل لمسارات المصادقة. كما أصبح مسار SQLite موحدًا عبر `DatabasePathResolver`، وتُفعّل SQLite بوضع WAL و`foreign_keys` و`busy_timeout`، وتُنفذ عمليات الحجز الحساسة داخل معاملة مع إعادة فحص التداخل.

وُحّدت استجابات الأخطاء إلى `ProblemDetails` و`ValidationProblemDetails`، وأضيف `DomainConflictException` لتعريف تعارض الحجز كـHTTP 409. كما طُبقت قواعد التحقق والتطبيع على العملاء والسيارات والتواريخ في API وMVC، وأصبحت لوحة الإدارة تعرض تعارضات الحجز ورسائل الإدخال بصورة مفهومة دون كشف بيانات دخول التطوير.

في Flutter، أضيف استخراج آمن لأخطاء ProblemDetails والتحقق المحلي المطابق لسياسة الخادم، مع مسح الجلسة عند HTTP 401 وإظهار رسائل عربية لحالات 401/403/404/408/429، وإعادة تحميل السيارات بعد إنشاء الحجز، وإظهار خطأ تحميل الكتالوج بدل اعتباره قائمة فارغة. تم تحديث اختبار لون الثيم ليتوافق مع هوية Premium Luxury الحالية.

## ملاحظات إصدار متبقية

لا تزال تغطية Flutter الآلية مركزة على النماذج والثيم، ولا توجد اختبارات Widget كاملة لكل شاشة أو اختبار ضغط إنتاجي. كما أن حساب الإدارة ما يزال إعدادًا تطويريًا ثابتًا وليس نظام إدارة حسابات متعدد المستخدمين؛ لذلك يجب استخدام مزود هوية مؤسسي أو تخزين مجزأ لحسابات الإدارة قبل نشر النظام للعامة. هذه الملاحظات موثقة كتحسينات لاحقة وليست عوائق أمام تشغيل النسخة المحلية الحالية.
